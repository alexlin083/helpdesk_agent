# 組員知識庫資料提交指南

本資料夾供組員蒐集、撰寫與審核知識庫段落。每筆資料應能獨立回答一個主題，包含適用條件、處理步驟、例外及人工處理條件。

此處的 Markdown 不會被後端自動載入。審核後才由專案負責人整合到 `../knowledgeBase.json`；目前系統主要讀取 `doc_name`、`content`，其他欄位供資料管理及未來前端擴充使用，尚未全部回傳或顯示。

## 文件與分工

| 文件 | 用途 |
| --- | --- |
| [單筆資料填寫範本](單筆資料填寫範本.md) | 複製後逐筆填寫；主資料與驗證情境分開 |
| [IT 資訊服務台範例](IT資訊服務台範例.md) | VPN、權限申請、未知問題受理，共三筆 |
| [HR 人力資源部範例](HR人力資源部範例.md) | 請假流程、補打卡、薪資明細確認，共三筆 |
| [總務與硬體組範例](總務與硬體組範例.md) | 設備借用、設備故障、設備冒煙，共三筆 |

程式的 departments 有四個意圖對應，但只有三個不同部門；`UNKNOWN` 同樣歸 `IT資訊服務台`。因此提供三部門各三筆，共九筆，其中一筆涵蓋 UNKNOWN。

所有範例均為 **SIMULATED 課堂模擬資料**，未經企業確認，不是正式規章、法律依據或實際聯絡資訊。日期代表範例整理日期，並不代表企業已審核。

## 主資料必填欄位

以下十一個 key 均須提供；`source_url` 沒有可分享的網址時填 JSON 的 `null`，不要寫字串 `"null"`。

| Key | 型別 | 填寫方式 | 預計用途 |
| --- | --- | --- | --- |
| `id` | string | 全資料庫唯一，如 `IT-001`、`HR-001`、`FAC-001`；更新同筆時沿用 | 追蹤段落 |
| `category` | string | 限下表的 INTENTS 值 | 分類與檢索管理 |
| `doc_name` | string | 原始文件名稱；相同文件的多個段落可共用 | 前端來源文件名稱 |
| `section_title` | string | 本段的具體主題 | 前端段落標題 |
| `content` | string | 自足的完整內容，明列適用條件、步驟、例外及人工處理條件 | 提供 AI 回答依據 |
| `summary` | string | 一至兩句摘要，不能加入正文沒有的規則 | 前端來源卡片摘要 |
| `department` | string | 只能使用對應部門的完整名稱 | 流程權責部門 |
| `version` | string | 如 `1.0`；若自訂整理版號須註明，勿冒充正式文件版號 | 版本追蹤 |
| `updated_at` | string | `YYYY-MM-DD`；填實際最後核對／整理日期 | 日期顯示與維護 |
| `source_url` | string 或 null | 原始資料的可存取網址；沒有、無權公開或僅本機檔案則填 null | 未來的來源連結 |
| `data_status` | string | `OFFICIAL`、`PENDING_REVIEW`、`SIMULATED` | 區分正式、待確認與模擬資料 |

`data_status` 是本蒐集文件的管理約定，目前不會自動控制後端是否載入；整合者仍須人工審核。內部資料若無公開網址，應在正文外的「來源與審核」紀錄文件章節、版本及核對方式，不必編造網址。

## 固定意圖與部門對應

以 `../../services/geminiAgent.js` 的定義為準，不自行增加縮寫或新值。

| category／INTENTS | department | 適用範圍 |
| --- | --- | --- |
| `IT_SUPPORT` | `IT資訊服務台` | 帳號、網路、軟體、權限與資訊服務 |
| `HR_POLICY` | `HR人力資源部` | 人事流程與規章 |
| `HARDWARE_FACILITY` | `總務與硬體組` | 實體設備、資產與環境報修 |
| `UNKNOWN` | `IT資訊服務台` | 無法辨識主題時的初步受理，不是其他所有專業問題的通用答案 |

知識段落的 category 表示資料主題；驗證情境的 expected_intent 表示某一個問題預期的辨識結果，不能把段落分類當成本次 AI 判斷的保證。

## 驗證情境與固定處置選項

每筆主資料另附至少一筆「驗證情境」，建議另補兩種不同問法。驗證情境不混入 content，也不直接當成檢索文件。

| 情境欄位 | 填寫規則 |
| --- | --- |
| `message` | 使用者可能自然輸入的問題，不含個資或密碼 |
| `expected_intent` | 僅限四個 INTENTS 值 |
| `expected_action_route` | 僅限 `AUTO_REPLY`、`ESCALATE_TICKET` |
| `expected_level` | AUTO_REPLY 填 null；ESCALATE_TICKET 限 `P1_URGENT`、`P2_HIGH`、`P3_NORMAL` |
| `expected_department` | AUTO_REPLY 填 null（沒有工單）；ESCALATE_TICKET 填上表對應部門 |
| `expected_reply_points` | 必須涵蓋的回答重點陣列，不要求逐字一致 |

`null` 表示不產生工單，不是新增的 LEVELS 或 departments 值。P1 表示需立即人工處理的緊急情境，P2 表示高優先情境，P3 表示一般人工處理；組員需在原始依據或模擬政策中寫明選擇理由，不能只憑感覺標註。

AUTO_REPLY 表示有足夠依據、可直接回答；ESCALATE_TICKET 表示需核准、人工確認、依據不足或涉及風險。這些是驗證預期，不是寫死 AI 的回答。實際回應仍由檢索、模型及後端驗證產生，現有門檻為自動回答至少 75 分、轉派低於 75 分。

不要手填 `relevance`、`confidence_score` 或 `ticket_id`：它們由執行時的後端或模型產生。`department` 在主資料表示權責部門；`expected_department` 才表示驗證情境的預期工單部門。

## 組員交付方式

1. 複製填寫範本，檔名可用 `IT-004_無線網路連線.md`，一檔一主題。
2. 先確認是否有相同主題，避免新增互相矛盾的版本。
3. 填完十一個主資料欄位與獨立驗證情境。
4. 補上來源章節、適用版本、蒐集及審核紀錄。只有實際核對並取得使用授權的資料才標 OFFICIAL。
5. 審核者核對分類／部門對應、內容可執行性、例外與人工處理條件，再交給專案負責人整合。

不要蒐集或提交實際登入密碼、API 金鑰、JWT、員工個資或無權分享的內部文件。沒有證據的電話、規定、網址與處理期限不要編造；課堂模擬內容需在 content 和 data_status 中都清楚標示。
