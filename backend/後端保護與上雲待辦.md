## HTTP 請求頻率保護：已實作

帳號的 10 秒冷卻、每日 30 次、單帳號並行 1 筆、全站並行 2 筆與每日 100 次已實作。這些是 Agent 業務限制，與以下 HTTP 層限制分開。

以下為已實作的預設值，可透過 .env.example 對應的 HTTP_*／LOGIN_* 參數調整。仍須依課前測試及日誌調整，不能保證適用所有學校出口流量。

| 層級 | 預設值 | 用途與實作位置 |
| --- | --- | --- |
| 全 API 的粗粒度 IP 限制 | 每 IP 每分鐘 300 次 | 在解析 JSON、JWT 驗證、配額儲存之前擋異常大量請求；健康檢查及 OPTIONS 排除，不拿來計算每日額度 |
| 登入總請求 | 每 IP 每分鐘 120 次 | 包含成功／失敗，在昂貴處理及資料庫之前檢查，避免反覆正確登入消耗資源 |
| 已登入的用量查詢 | 每 userID 每分鐘 30 次 | JWT 驗證後、讀取儲存之前檢查；前端不需每秒輪詢 |
| 已登入的聊天 HTTP 請求 | 每 userID 每分鐘 12 次 | 包含被業務限制拒絕的請求；在配額儲存前檢查，另保留原有冷卻／並行／每日額度 |
| 登入失敗 | 已知帳號＋IP 的短期計數 | 已知帳號每組合 5 次／5 分鐘；另保留 IP 失敗總數 100 次／15 分鐘，避免同 IP 不同帳號互相拖累 |

未知帳號只累積 IP 整體失敗，不使用任意 username 建立新計數。HTTP 各 middleware 最多追蹤 2048 筆；登入失敗原子狀態最多 512 筆。到期項目於後續請求清除；容量滿載拒絕新識別碼，不淘汰有效保護。IPv6 來源皆使用 /64 分組。

這些是上限，不是保證所有請求成功；全站並行只有 2 筆，其他同學會收到既有 503／SERVICE_BUSY，稍後再手動送出。每日總額 100 次十組共用，達到上限仍會停止當日新問題，不是 Wi-Fi 被封鎖。

已維持統一錯誤 JSON、429 與實際剩餘秒數 Retry-After，並測試同 IP 十組帳號的隔離、登入與送問、HTTP 拒絕不扣 Agent 額度及有界計數到期。HTTP 計數使用單程序記憶體，重啟歸零；多 instance 各自生效，跨 instance 保護仍需要共享儲存或入口代理。登入失敗沿用 LIMIT_STORE，與 HTTP 請求計數分開。

## 學校 Wi-Fi 與目前實際影響

學校 Wi-Fi 可能經 NAT 共用公用 IP，也可能有多個出口或 IPv6；不能僅由連上同一 Wi-Fi 判斷每人的對外 IP。

目前正常聊天的配額與冷卻依 JWT 內的 userID 計算，不因共用 IP 而合併；每人應分配不同帳號。共用同一帳號則會共用冷卻、並行與每日額度。

已依使用者確認更新登入失敗規格：已知帳號＋IP 每 5 分鐘五次，來源整體每 15 分鐘一百次。單一組合被封鎖不會連帶封鎖同 IP 其他帳號；若來源整體也超限，其他帳號仍需等待。未封鎖前成功登入只清除該帳號組合，IP 整體失敗保留至到期。

`.env` 或平台環境參數優先於預設。舊部署若仍設 LOGIN_FAILURE_LIMIT=10，應改為 100，並新增 LOGIN_ACCOUNT_FAILURE_LIMIT=5／LOGIN_ACCOUNT_WINDOW_SECONDS=300；本次未覆寫私人 .env。

上雲後 `TRUST_PROXY` 必須依實際負載平衡器／反向代理路徑設定，不能任意設為信任所有標頭。否則可能將所有學生誤認為代理 IP，或允許偽造 IP。參考 [Express 官方代理設定說明](https://expressjs.com/en/guide/behind-proxies/)。

## DynamoDB：依使用者要求暫緩

目前尚未啟用 DynamoDB；本次不建立表格、不設定 IAM、不連接 AWS、不執行實際 DynamoDB 整合驗證，也不改動現有 DynamoDB 儲存實作。

保留既有模擬測試不等於已驗證雲端可用。以下待啟用時處理：

- 資料表、區域、IAM 最小權限、條件寫入及多 instance 競爭測試。
- 網路逾時、節流、重試與租約釋放故障測試，確認失敗時不退回記憶體放行。
- 日誌補充安全的 AWS 錯誤類型、狀態及 request ID，避免輸出原始請求或機密。
- 儲存服務就緒檢查；現有 `/api/health` 只表示程序存活，不代表 DynamoDB 或 Gemini 可用。
- 根據實際儲存延遲及平台終止寬限，驗證 Agent 期限、租約 180 秒與關機期限的協調。

**目前 production 仍強制要求 DynamoDB**，並未為了暫緩而放寬。現階段使用 development + memory 本機驗證；正式上雲前須完成上述工作或另行設計經同意的儲存方案。記憶體模式重啟會歸零，只支援單程序。

## 掛載與驗證

- middleware/rateLimiter.js：四種 HTTP 限流及有容量上限的獨立儲存。
- server.js：日誌 → CORS → API IP 保護 → 登入總請求保護 → JSON → 路由 → 錯誤處理。
- routes/agentRoutes.js：驗證 JWT → 帳號 HTTP 保護 → controller／用量儲存。
- services/usageService.js：兩層登入失敗視窗的原子檢查、更新及到期復原。
- tests/rateLimiter.test.js：同 IP 十組身分隔離、HTTP 超限不扣額、健康／CORS 排除、JSON 前拒絕、來源失敗累積、未知帳號有界及 IPv6 防繞過。
- http.rate_limit.blocked 日誌提供 api／login／chat／usage 原因；不輸出原始 IP、帳密或 token。
