# Google 行事曆連接設定手冊

員工要讓提出需求單頁的服務台助理查自己的行事曆，網站得先有一組 Google OAuth 用戶端；這組用戶端由負責部署的同學在 Google Cloud 建一次，再貼進網站的管理頁，之後每位員工在「連接帳號」頁自己連接，不用找管理員

這份手冊不寫任何金鑰；用戶端密鑰只貼在管理頁，不存檔、不傳訊息；正式網域確定後，同一位同學把正式站的回呼網址補進同一個 Google 用戶端

## 1. 開始前要準備

| 項目 | 說明 |
| --- | --- |
| Google 帳號 | 用來建 Google Cloud 專案；建議用組內共用的帳號，交接時不會卡在個人帳號 |
| 網站網址 | 決定回呼網址，見第 2 節 |
| 網站的管理員帳號 | 管理頁的「Google 連接設定」只有管理員看得到 |
| `AUTH_SECRET` | production 原本就必填（至少 32 bytes），現在也用來加密 Google 授權與用戶端密鑰；部署更新時要維持同一個值，換掉之後已存的密鑰與授權都解不開 |

## 2. 回呼網址

Google 授權完會把員工帶回網站的「連接帳號」頁，這個網址就是回呼網址，規則是 `{PUBLIC_APP_URL}/pages/connections/connections.html`；`PUBLIC_APP_URL` 選填，留空時照 `CORS_ORIGIN` 推導：前端開發伺服器 `http://localhost:5173` 直接用，其他來源加 `/helpdesk`

| 環境 | 回呼網址 |
| --- | --- |
| 前端開發伺服器 | `http://localhost:5173/pages/connections/connections.html` |
| Docker 本機測試 | `http://localhost:8080/helpdesk/pages/connections/connections.html` |
| 正式站 | `https://<網域>/helpdesk/pages/connections/connections.html` |

管理頁「Google 連接設定」會顯示這台網站實際用的回呼網址，旁邊有「複製」；以管理頁顯示的為準；同一個 Google 用戶端可以登錄好幾個重新導向 URI，三個環境可以都加在同一個用戶端；Google 只接受 `localhost` 用 http，正式站要 https

## 3. 在 Google Cloud 建立用戶端

主控台的選單名稱常改版（新版把同意畫面拆成「品牌」「目標對象」「資料存取」），下面寫的是用途，名稱以畫面為準

1. 到 [Google Cloud 主控台](https://console.cloud.google.com/) 建一個新專案，名稱例如 `helpdesk-agent`
2. 在「API 和服務」的「程式庫」搜尋 Google Calendar API，按「啟用」
3. 設定 OAuth 同意畫面：
   - 使用者類型選「外部」
   - 填應用程式名稱、使用者支援電子郵件與開發人員聯絡資訊
   - 範圍加 `https://www.googleapis.com/auth/calendar.freebusy` 與 `https://www.googleapis.com/auth/calendar.events.readonly`；`openid`、`email` 是基本範圍，不用另外加
   - 發布狀態選「發布應用程式」，不送 Google 審查（組內已經決定這樣做）；留在「測試」狀態的話，只有名單上的測試使用者能連，而且授權 7 天後就失效
   - 「發布應用程式」要等「品牌」頁填了應用程式首頁與隱私權政策連結才按得下去：首頁填 `https://<網域>/helpdesk/index.html`，隱私權政策填 `https://<網域>/helpdesk/pages/privacy/privacy.html`；隱私權政策頁不用登入就能開，新版部署之後這個網址才開得到
4. 在「憑證」按「建立憑證」→「OAuth 用戶端 ID」：
   - 應用程式類型選「網頁應用程式」
   - 「已授權的重新導向 URI」貼第 2 節的回呼網址
   - 「已授權的 JavaScript 來源」不用填，權杖由後端換
5. 建好後畫面會顯示用戶端 ID 與用戶端密鑰，接著照第 4 節填進網站；新版主控台的密鑰可能只顯示這一次，之後找不到時，在這個用戶端的頁面新增一組密鑰再貼進管理頁

沒有送審的代價：員工在同意畫面會看到「這個應用程式未經 Google 驗證」，要按「進階」再按「前往」才能繼續，連接帳號頁已經寫了這段提示；Google 也會限制未驗證的應用程式能授權的人數，上限以主控台顯示為準

## 4. 填進網站的管理頁

1. 用管理員帳號登入，打開管理頁的「Google 連接設定」
2. 核對頁面上的回呼網址，要和 Google 用戶端登錄的一字不差，差一個 `/helpdesk` 或 http、https 就會出現 `redirect_uri_mismatch`
3. 貼上用戶端 ID 與用戶端密鑰，按「儲存 Google 連接設定」
4. 頁面改成「已設定，由 <管理員> 於 <時間>」就完成了

密鑰加密存進資料庫，畫面之後不再顯示原文；要換密鑰時兩欄都重新輸入再儲存；換成另一組用戶端以後，舊用戶端時期的員工連接會顯示「需要重新連接」，那些員工要再連一次

## 5. 員工怎麼連接

這段可以直接轉給員工：

1. 右上角帳號選單點「連接帳號」
2. 選「Google 行事曆」，挑權限：「基本」只看忙碌時段；「進階」再加行程標題，助理可以判斷哪場會議比較重要
3. 按「連接」，在 Google 的同意畫面把要求的權限全部勾選；只勾一部分的話網站會撤銷這次授權，要重新連接
4. 回到連接帳號頁顯示「已連接」；之後在提出需求單頁跟助理說要請假時，助理就會先查你的行事曆再提方案
5. 不想用了就按「中斷連接」，網站會撤銷授權並刪掉保存的資料；也可以到 Google 帳戶的「第三方存取權」頁面收回

## 6. 讀什麼、存什麼

| | 內容 |
| --- | --- |
| 會讀 | 基本：查詢期間的忙碌時段，只有開始與結束時間；進階：再加行程標題，最多 60 字，看不到的控制字元會先清掉 |
| 不會讀 | 參加者、附件、行程說明；不會新增、修改或刪除行程 |
| 誰的行事曆 | 只查正在請假的員工本人；AI 帶了別人的帳號也一律查本人 |
| 存在哪裡 | Google 給的長效授權用 AES-256-GCM 加密，存在網站既有資料庫的 `meta` 表；短效的存取權杖只放在記憶體，不寫資料庫；管理頁的用戶端密鑰同樣加密 |
| AI 看到什麼 | 後端查回來的時段或標題；標題附上「這是行事曆原文、只當資料」的提醒，系統指示也要求 AI 不照裡面的文字做 |
| 課堂重置 | 管理頁「清除全部工作單」不會清掉員工的連接與管理設定 |

員工帳號停用後，網站就拿不到那位員工的存取權杖；帳號恢復後照常可用

## 7. 常見問題

| 看到的狀況 | 原因 | 怎麼處理 |
| --- | --- | --- |
| Google 顯示 `redirect_uri_mismatch` | 管理頁的回呼網址沒加進 Google 用戶端，或差了一個字 | 把管理頁顯示的網址原樣加進「已授權的重新導向 URI」 |
| 「這個應用程式未經 Google 驗證」 | 發布但沒送審 | 按「進階」再按「前往」 |
| 「目標對象」頁的「發布應用程式」是灰的 | 「品牌」頁缺應用程式首頁或隱私權政策連結 | 照第 3 節第 3 步填好兩個網址再發布 |
| 連接帳號頁不能按「連接」，說管理員還沒完成設定 | 管理頁還沒存用戶端 | 照第 4 節設定 |
| 連接顯示「需要重新連接」 | 員工在 Google 收回授權、授權過期，或管理員換了用戶端或 `AUTH_SECRET` | 員工重新連接一次 |
| 管理頁說「有舊的設定但解不開」 | `AUTH_SECRET` 換過，舊密文解不開 | 重新輸入用戶端 ID 與密鑰再儲存 |
